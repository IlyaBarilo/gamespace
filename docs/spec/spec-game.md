# 🎮 Спецификация автономных HTML-игр для GameSpace и браузера

Документ описывает требования к автономным HTML-играм, предназначенным для запуска на интерактивных экранах, touch-панелях, смартфонах, планшетах и обычных компьютерах с поддержкой мыши, touch и клавиатуры там, где игровая механика допускает клавиатурное управление.

Документ предназначен для разработчика игры и ИИ-ассистента, который её создаёт.
Он задаёт требования к реализации, UX, вводу, масштабированию, производительности, завершению раунда и повторному запуску игры.

Он нужен для:
- разработки игр вручную;
- генерации игр через ИИ;
- проверки качества и совместимости игры на разных типах устройств;
- создания полностью автономных игр, работающих без обязательных внешних сервисов.

Файл специально оформлен так, чтобы его мог читать и человек, и ИИ-ассистент:
его можно прикладывать к запросу на генерацию игры как технический контракт.

Документ описывает:
- как должна запускаться автономная игра;
- как должен быть организован игровой цикл;
- как должна работать повторная игра после завершения;
- какие требования обязательны для UX, ввода, масштабирования и завершения игры;
- какие ошибки считаются нарушением спецификации.

---

## 📌 Общая идея

Игра — это автономный HTML-файл. **Каждая игра должна находиться в отдельном `.html`-файле: один файл = одна игра.** Несколько самостоятельных игр не должны объединяться в один HTML-файл или выбираться внутри него через внутреннее меню/роутер.

Игра:
- запускается прямым открытием в браузере, по обычной ссылке или внутри `iframe`/оболочки интерактивного экрана;
- полностью инициализирует своё состояние локально;
- обрабатывает игровой результат локально;
- работает без обязательного доступа к интернету;
- запускает игровой процесс сразу после локальной инициализации;
- после завершения показывает понятный итог;
- обязательно позволяет запустить новую игру кнопкой `Играть ещё раз` без перезагрузки страницы;
- может содержать кнопку `Завершить игру` / `Выйти`, возвращающую пользователя к странице, из которой была открыта игра.

---

## 🔄 Жизненный цикл игры

Стандартный жизненный цикл:

1. загрузка HTML;
2. локальная инициализация игры;
3. автоматический запуск игрового раунда;
4. игровой процесс;
5. завершение раунда;
6. показ итогового экрана;
7. нажатие `Играть ещё раз`;
8. полный сброс состояния;
9. запуск нового раунда в том же HTML-документе.

В любой момент, если это предусмотрено интерфейсом конкретной игры, пользователь может нажать `Завершить игру` / `Выйти`. Эта команда завершает взаимодействие с текущей игрой и инициирует возврат к странице, из которой она была открыта. Правила возврата описаны ниже отдельно для обычного окна и `iframe`.

Игра не должна требовать отдельного обязательного стартового экрана, подтверждения запуска или предварительного экрана с описанием правил, если это прямо не указано в задании конкретной игры.

Если механика требует короткого пояснения, оно должно быть встроено непосредственно в игровой интерфейс или первые игровые действия и не должно блокировать начало игры.

Запрещено использовать `location.reload()`, переходы через `location`, ссылки, формы или meta refresh для повторного запуска игры.

## 🧱 Автономность игры

Игра должна быть самодостаточной.

Требования:
- каждая игра должна находиться в своём отдельном HTML-файле;
- один HTML-файл должен содержать ровно одну самостоятельную игру;
- весь CSS и JavaScript конкретной игры должны находиться внутри этого же HTML-файла;
- игра не должна требовать CDN;
- игра не должна требовать API;
- игра не должна требовать сетевого соединения;
- запрещены обязательные внешние шрифты, стили, скрипты и медиа;
- изображения, звуки и другие ресурсы при необходимости должны быть встроены в HTML или создаваться средствами JavaScript;
- игровой процесс не должен зависеть от ответа внешнего сервера;
- игра должна корректно запускаться локально.

Запрещены как обязательная часть работы игры:
- `fetch`;
- `XMLHttpRequest`;
- `WebSocket`;
- `EventSource`;
- `navigator.sendBeacon`;
- динамический `import()` внешних модулей;
- `<script src>` на внешние ресурсы;
- внешние CSS-файлы;
- вложенные `iframe`, `object`, `embed`;
- открытие новых окон;
- автоматические загрузки файлов;
- произвольные попытки изменить адрес текущей страницы, кроме явно разрешённого пользовательского действия `Завершить игру` / `Выйти` для возврата назад в top-level режиме.

## 🔒 Рекомендуемая политика безопасности

Для полностью автономной игры рекомендуется использовать CSP, запрещающую сетевые подключения и внешние ресурсы.

В `<head>` до первого `<script>`, `<style>` или ресурса рекомендуется разместить:

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; media-src data: blob:; font-src data:; connect-src 'none'; frame-src 'none'; object-src 'none'; worker-src 'none'; manifest-src 'none'; base-uri 'none'; form-action 'none'">
```

Политика разрешает встроенные CSS и JavaScript, а также встроенные `data:`/`blob:` медиа, но не разрешает сетевые запросы и загрузку внешних документов.

CSP не заменяет корректную реализацию игры.

Длительные вычисления должны быть разбиты на небольшие шаги. Запрещены блокирующие циклы, способные заморозить интерфейс браузера.

## ▶️ Запуск игры

Игра должна быть готова к взаимодействию сразу после завершения локальной инициализации.

Требования:
- не должно быть искусственной задержки перед стартом;
- отдельная кнопка `Начать` не требуется, если она не является частью дизайна конкретной игры;
- игровой раунд запускается автоматически;
- все необходимые значения сложности, скорости, времени, цели и других параметров должны задаваться локально в конфигурации игры;
- параметры, которые разработчик должен иметь возможность быстро изменить, должны быть вынесены в понятный конфигурационный блок.

### 🎚 Сложность через URL (`?diff=`)

Каждая игра обязана поддерживать параметр URL `diff`:

```text
game.html?diff=3
```

Допустимые значения сложности — только целые числа от `1` до `5`:
- `1` — самая низкая сложность;
- `2` — ниже средней;
- `3` — средняя сложность;
- `4` — выше средней;
- `5` — самая высокая сложность.

Если параметр `diff` отсутствует, пуст, не является целым числом или выходит за диапазон `1..5`, игра обязана использовать значение `3`.

Полученное значение должно реально влиять на игровую механику. Недостаточно только сохранить `difficulty` в переменной. В зависимости от игры сложность может изменять, например:
- скорость объектов;
- частоту появления препятствий или целей;
- доступное время;
- размер цели или зоны попадания;
- количество объектов;
- скорость противников;
- допустимое количество ошибок;
- целевой счёт.

Рекомендуемый разбор параметра:

```js
function readDifficulty() {
  const raw = new URLSearchParams(window.location.search).get('diff');
  const value = Number(raw);
  return Number.isInteger(value) && value >= 1 && value <= 5 ? value : 3;
}

const CONFIG = {
  difficulty: readDifficulty(),
  roundTime: 45,
  targetScore: 20,
  playerSpeed: 460,
  acceleration: 900
};
```

Конкретная формула влияния сложности определяется механикой игры, но `diff=3` должен соответствовать базовой/средней настройке игры.

### 📱 Режим интерфейса через URL (`?ui=`)

Игра должна поддерживать необязательный параметр `ui`, который передаёт подсказку о целевом способе отображения:

```text
game.html?diff=3&ui=mobile
game.html?diff=3&ui=tv
```

Допустимые значения:
- `mobile` — телефон или планшет: крупные элементы управления для работы пальцем с близкого расстояния;
- `tv` — интерактивная панель, киоск или большой экран: увеличенный интерфейс, рассчитанный на просмотр с расстояния.

Если параметр отсутствует или содержит другое значение, игра должна автоматически выбрать оформление по размеру области просмотра и доступному типу указателя. Параметр является подсказкой для интерфейса и не должен менять правила, скорость или сложность игры.

GameSpace может определить подходящий режим и передать его каталогу. Каталог, открывающий игру, должен сохранить `ui=mobile` или `ui=tv` в адресе игры вместе с другими параметрами, включая `diff`. Явно переданное корректное значение имеет приоритет над автоматическим определением.

Физическое разрешение и `devicePixelRatio` нельзя использовать как единственный признак режима. Телефон с экраном высокого разрешения может иметь небольшую область в CSS-пикселях, а системное масштабирование компьютера изменяет доступный размер окна. `devicePixelRatio` используется для чёткости canvas, а не для определения читаемого размера текста.

## ⏱ Игровая логика и независимость от FPS

Если в игре есть управляемые или движущиеся объекты, их скорости, ускорения и максимальные пределы должны быть явно заданы в коде через отдельные переменные, коэффициенты или параметры конфигурации, а не скрыты внутри трудноизменяемых формул.

Перемещение, ускорение, замедление, таймеры и иные изменения состояния, зависящие от времени, не должны зависеть от:
- FPS;
- частоты обновления экрана;
- производительности устройства.

Такая логика должна рассчитываться с учётом времени между кадрами (`delta time`, `dt`).

Рекомендуемый принцип:

```js
const now = performance.now();
const dt = Math.min((now - lastTime) / 1000, 0.05);
lastTime = now;

player.x += player.vx * dt;
player.y += player.vy * dt;
```

Ограничение `dt` рекомендуется для предотвращения больших скачков после возврата на вкладку или временной остановки рендеринга.

Изменение разрешения экрана или размера canvas не должно менять время прохождения одинаковой относительной дистанции по игровому полю, если это не является явной частью механики.

## 🏁 Завершение игрового раунда

Завершение раунда — это локальное состояние игры, после которого текущий результат больше не должен изменяться до нового запуска.

При завершении раунда игра должна:
- остановить изменение игрового результата;
- остановить игровую механику текущего раунда;
- прекратить влияние игрового ввода на завершённый раунд;
- показать понятный итог;
- оставить активным финальный интерфейс;
- обязательно показать кнопку `Играть ещё раз`.

После завершения игрового раунда запрещено:
- продолжать начислять очки;
- продолжать уменьшать игровой таймер;
- создавать новые игровые объекты текущего раунда;
- позволять игровым жестам менять итог завершённого раунда;
- запускать вторую копию игрового цикла поверх первой.

При этом финальный UI остаётся интерактивным.

## 🚪 Завершение игры и возврат на предыдущую страницу

Игра может содержать явно видимую кнопку `Завершить игру` / `Выйти`. Для интерактивных экранов рекомендуется размещать её так, чтобы она была доступна, но не мешала основному управлению и не нажималась случайно.

Кнопка должна работать по-разному в зависимости от способа запуска.

### Обычное открытие страницы

Если игра открыта как самостоятельная top-level страница (`window.self === window.top`), по явному нажатию пользователя допускается выполнить:

```js
if (window.history.length > 1) {
  window.history.back();
}
```

Это позволяет вернуться к предыдущей записи истории браузера, если она существует.

Важно:
- браузер не предоставляет игре гарантированный способ узнать «страницу, с которой пришли» во всех режимах;
- `document.referrer` может быть пустым и не должен считаться обязательным механизмом возврата;
- при прямом открытии файла, из закладки или в новой вкладке предыдущей подходящей записи истории может не быть;
- игра не должна автоматически перенаправлять пользователя без явного нажатия кнопки выхода.

### Запуск внутри `iframe`

Если игра запущена внутри `iframe`, она **не должна пытаться напрямую управлять историей или DOM родительской страницы**. Это может быть запрещено политикой same-origin или `sandbox`.

Вместо этого при нажатии `Завершить игру` игра отправляет родительской странице нейтральный сигнал:

```js
window.parent.postMessage({ type: 'gameExit' }, '*');
```

`gameExit` — это только опциональный универсальный сигнал контейнеру о выходе из игры. Он не является протоколом результатов игры и не передаёт счёт, сложность или другие игровые данные.

Родительская страница должна сама определить действие: например, скрыть/удалить `iframe`, вернуть каталог игр или выполнить собственный переход назад.

GameSpace PWA обрабатывает этот сигнал на уровне оболочки: проверяет, что сообщение пришло от открытого игрового iframe, и возвращает в исходный каталог. Игра не должна обращаться к API оболочки или знать адрес каталога.

Пример обработчика на странице-контейнере:

```js
const gameFrame = document.getElementById('gameFrame');

window.addEventListener('message', (event) => {
  if (event.source !== gameFrame.contentWindow) return;
  if (!event.data || event.data.type !== 'gameExit') return;

  gameFrame.remove();
  // Здесь контейнер возвращает свой экран/каталог или выполняет нужную навигацию.
});
```

Если `iframe` использует `sandbox`, для работы самой HTML-игры должен быть разрешён JavaScript (`allow-scripts`). Разрешение `allow-top-navigation` игре для выхода **не требуется**, потому что возврат выполняет родитель после получения `gameExit`.

Игра может быть встроена во `iframe`; запрет вложенных `iframe` в разделе автономности означает только то, что **сама игра не должна создавать дополнительные iframe внутри себя**.

## 🔁 Повтор игры

Кнопка `Играть ещё раз` обязательна на финальном экране.

Повтор должен выполняться внутри текущего HTML-документа без перезагрузки страницы.

При повторе необходимо полностью сбросить состояние предыдущего раунда.

В зависимости от механики должны быть сброшены:
- счёт;
- таймер;
- статус победы/поражения;
- позиции объектов;
- скорости и ускорения;
- состояние игрока;
- состояние противников;
- созданные снаряды, препятствия, бонусы и другие временные объекты;
- активные эффекты;
- временные классы DOM;
- временные canvas-объекты;
- состояние drag/hold/joystick;
- активный `pointerId`;
- локальные флаги завершения;
- интервалы и таймеры, относящиеся к прошлому раунду.

Новый раунд не должен наследовать случайные побочные состояния предыдущего раунда, если это не предусмотрено механикой специально.

### Требование к таймерам и циклам

`restartGame()` не должен создавать дублирующиеся `requestAnimationFrame`, `setInterval` или обработчики событий.

Рекомендуется:
- иметь один постоянный animation loop и переключать состояние `gameActive`;
- либо перед новым запуском явно отменять старый `requestAnimationFrame`;
- всегда очищать созданные `setTimeout` и `setInterval`;
- не навешивать повторно одни и те же обработчики событий при каждом рестарте.

## 🏆 Финальный статус игры

Финальный экран должен однозначно показывать, чем закончился текущий раунд.

Требования:
- победа должна визуально считываться как победа;
- поражение не должно визуально выглядеть как успех;
- если есть целевой счёт, время или другое условие, итоговый статус должен определяться фактическим выполнением этого условия;
- текст, иконки и общий визуальный тон финального экрана не должны противоречить фактическому результату;
- если игра использует промежуточные оценки, они не должны скрывать основной итог;
- на финальном экране должна быть кнопка `Играть ещё раз`.

Допускается вывод:
- итогового счёта;
- времени;
- точности;
- количества выполненных целей;
- другого локального результата игры.

Передача технического числового кода во внешний движок не требуется.

---

## 📊 HUD и игровые индикаторы

- если элемент выглядит как прогрессбар, он обязан показывать реальное значение;
- шкалы должны отражать счёт, прогресс до цели, время или другой настоящий ресурс;
- при превышении цели шкала остаётся заполненной на 100%, если механика не предусматривает другое поведение;
- игрок должен понимать, что показывает каждый важный элемент HUD;
- декоративные элементы не должны ошибочно выглядеть как активные индикаторы;
- HUD не должен перекрывать критически важную игровую область без необходимости.

## 🎮 UX

Игра должна:
- запускаться автоматически после локальной инициализации;
- не требовать отдельного обязательного экрана с описанием игры;
- не требовать обязательного подтверждения перед началом;
- не создавать искусственную паузу перед стартом;
- ясно показывать игровые цели через сам интерфейс и механику;
- быть рассчитана на короткое и понятное взаимодействие;
- по умолчанию быть оптимизирована под вертикальную ориентацию экрана, если в задании явно не указано иное;
- не требовать скролла внутри игрового интерфейса;
- иметь крупные и удобные для касания интерактивные элементы.

Рекомендуемая продолжительность одного раунда: не более 60 секунд, если механика не требует другого.

Не следует оставлять игрока без действия более чем на 1–2 секунды без явной причины.

## 🖐 Обработка ввода и совместимость устройств (ОБЯЗАТЕЛЬНО)

Одна и та же игра ОБЯЗАНА корректно работать на всех целевых типах устройств:
- компьютеры и ноутбуки с мышью / тачпадом и клавиатурой;
- смартфоны;
- планшеты;
- интерактивные экраны / touch panels / kiosk screens;
- иные совместимые устройства с pointer-, mouse-, touch- или keyboard-вводом.

Недопустима реализация, которая корректно работает только на одном классе устройств и нестабильна или неработоспособна на остальных.

Требования:
- игра обязана поддерживать mouse-ввод;
- игра обязана поддерживать touch-ввод;
- если игровая механика может естественно управляться клавишами (направление, движение, выбор, прыжок, действие, подтверждение и другие дискретные команды), игра обязана поддерживать keyboard-ввод как дополнительный способ управления на устройствах с клавиатурой;
- клавиатура не должна быть единственным способом прохождения игры: обязательная поддержка mouse/touch сохраняется;
- для механик, принципиально основанных на свободном drag, рисовании, мультитаче или точном позиционировании указателя, полная клавиатурная замена не обязательна, если иное прямо не указано в задании игры;
- для направления и движения рекомендуется поддерживать одновременно `WASD` и клавиши стрелок;
- для основного дискретного действия рекомендуется использовать `Space` и/или `Enter`, если это не конфликтует с механикой и UI;
- длительное действие или движение с клавиатуры должно корректно обрабатываться через состояние нажатых клавиш (`keydown` / `keyup`), а не зависеть от частоты автоповтора браузера;
- одноразовые действия на `keydown` не должны многократно срабатывать из-за `event.repeat`, если повтор не предусмотрен механикой;
- состояние зажатых клавиш должно очищаться при завершении раунда, повторе игры, `window.blur` и потере видимости документа, чтобы управление не оставалось «залипшим»;
- глобальные keyboard-обработчики не должны запускать игровую механику, когда фокус находится в `input`, `textarea`, `select`, элементе с `contenteditable` или на интерактивном UI, например кнопке;
- игровые клавиши, которые могут прокручивать страницу (`Arrow*`, `Space` и другие при необходимости), должны вызывать `preventDefault()` во время активного игрового управления, но не должны ломать стандартную работу UI;
- нативная клавиатурная активация кнопок через `Tab` + `Enter` / `Space` должна оставаться работоспособной;
- игра обязана корректно работать в средах, где touch приходит через Pointer Events, Touch Events или иную браузерно-совместимую модель;
- если среда поддерживает Pointer Events, они должны считаться основным каналом pointer/touch-ввода;
- Mouse Events и Touch Events в среде с поддержкой Pointer Events должны использоваться только как fallback при явном отсутствии нужного поведения через Pointer Events либо при наличии явной дедупликации одного физического ввода;
- запрещено одновременно обрабатывать один и тот же физический ввод через Pointer Events и через Touch/Mouse Events без явной защиты от двойного срабатывания;
- реализация должна явно определять стратегию маршрутизации pointer/touch-ввода: `Pointer Events first`, `fallback-only` либо эквивалентную схему без дублей;
- если механика использует удержание, drag, multitouch, joystick, непрерывное движение, ведение по траектории или быстрые касания, такая механика обязана корректно работать на всех соответствующих целевых устройствах;
- для drag, удержания или непрерывного ведения указателя реализация должна обеспечивать сохранение управления до завершения взаимодействия, например через Pointer Capture или эквивалентную fallback-логику;
- запрещено проектировать игру только под мышь;
- запрещено проектировать игру только под телефонный touch;
- запрещено проектировать игру только под интерактивный экран;
- если механика допускает клавиатурное управление, запрещено игнорировать клавиатуру на обычном компьютере;
- запрещено использовать `click` как единственный механизм ввода там, где требуется мгновенная реакция, удержание или непрерывное движение;
- обязательно должна обрабатываться отмена pointer/touch-ввода (`pointercancel`, `touchcancel` или эквивалентное завершение взаимодействия);
- управление должно ощущаться сопоставимо на разных устройствах и не должно заметно ломаться из-за различий в модели ввода, FPS, частоте обновления экрана или производительности устройства.

Практический смысл:
- одна и та же реализация должна реально работать мышью, пальцем на смартфоне и на интерактивном экране;
- на компьютере клавиатура должна давать полноценный дополнительный способ управления во всех механиках, которые разумно переводятся на клавиши;
- если игра работает только мышью — это нарушение спецификации;
- если игра работает только клавиатурой и не работает через mouse/touch — это нарушение спецификации;
- если механика допускает клавиши, но клавиатурное управление на компьютере отсутствует — это нарушение спецификации;
- если игра работает на смартфоне, но не работает на интерактивном экране — это нарушение спецификации;
- если игра работает на интерактивном экране, но ломается на обычном компьютере — это нарушение спецификации.

## 🔒 Изоляция UI от игровой логики (ОБЯЗАТЕЛЬНО)

Все UI-элементы — кнопки, панели, контролы, overlay-экраны, модальные окна, drag-handle, служебные панели и др. — должны быть полностью изолированы от игровой механики.

### 1. Проверка цели событий

Все обработчики игровой логики (`pointerdown`, `pointermove`, `pointerup`, `touchstart`, `touchmove`, `touchend`, `mousedown`, `mousemove`, `mouseup` и др.) должны проверять `event.target`.

Если `event.target` или его родитель относится к UI, обработчик игровой логики должен немедленно завершаться.

Рекомендуемая проверка:

```js
function isUiTarget(target) {
  return !!(
    target &&
    target.closest('.button, .panel, .overlay, .ui-control, [data-ui="true"]')
  );
}
```

### 2. Блокировка всплытия

Интерактивные UI-элементы должны предотвращать передачу событий в игровую механику.

Для нужных элементов должны корректно обрабатываться:
- `click`;
- `pointerdown`;
- `pointerup`;
- `touchstart`;
- `touchend`;
- `mousedown`;
- `mouseup`.

Если UI-элемент поддерживает перетаскивание, должны быть изолированы и его move-события.

### 3. Слои и приоритет

- UI должен находиться выше игрового слоя и визуально, и по приоритету ввода;
- UI-слой должен иметь `z-index` больше игрового canvas/контейнера;
- рекомендуется использовать отдельный верхний слой для интерактивного UI;
- при наложении UI на игровую область приоритет ввода всегда должен быть у UI.

### 4. Pointer events

- запрещено использовать `pointer-events: none` на контейнерах, через которые должен приниматься пользовательский ввод;
- `pointer-events: none` допустим только на чисто декоративных элементах;
- если нужен прозрачный слой поверх игры, интерактивные дочерние элементы должны оставаться доступными для ввода.

### 5. Общий запрет на смешивание UI и игровой логики

- нажатия по UI не должны запускать игровую механику;
- глобальные обработчики на `window`, `document` или общем контейнере не должны реагировать на события, пришедшие из UI;
- mouse fallback на `window` не должен дублировать Pointer Events;
- fallback-обработчики должны включаться только при отсутствии основного канала ввода либо быть логически изолированы от него;
- кнопка `Играть ещё раз` не должна одновременно считаться игровым касанием.

## 📐 Масштабирование интерфейса (ОБЯЗАТЕЛЬНО)

Игра должна раздельно масштабировать игровой мир и пользовательский интерфейс. Один коэффициент нельзя без ограничений применять одновременно к координатам игры, тексту и кнопкам: на телефоне это может уменьшить обычный шрифт до нечитаемого размера.

Для игрового мира и canvas рекомендуется базовый портретный размер:
- width = 810;
- height = 1440.

GameSpace открывает витрину и игру во внутренней области приложения. В портретной ориентации эта область занимает всю доступную ширину и высоту. В альбомной ориентации оболочка ограничивает её пропорцией `10:16`, сохраняет полную доступную высоту, центрирует и заполняет свободное место по бокам чёрным цветом. Эти размеры и поля принадлежат оболочке GameSpace, а не HTML-файлу игры. Игра должна занимать `100%` полученной области просмотра, адаптироваться к ней и не создавать собственный внешний фрейм или боковые поля.

Коэффициент игрового мира:

```text
worldScale = min(viewportWidth / 810, viewportHeight / 1440)
```

`worldScale` применяется к игровым координатам, размерам объектов и расстояниям игрового мира. Текст, HUD, кнопки, панели и зоны нажатия должны использовать отдельные CSS-размеры с нижней и верхней границей.

Минимальные размеры в CSS-пикселях:
- обычный текст — не менее `16px`;
- важный текст, HUD и подписи основных действий — не менее `18px`;
- зона касания кнопки или другого основного элемента — не менее `48 × 48px`;
- расстояние между соседними сенсорными действиями — не менее `8px`.

Для плавного увеличения рекомендуется использовать `clamp()`. Пример базовых переменных:

```css
:root {
  --text-size: clamp(16px, 2.2vmin, 28px);
  --hud-size: clamp(18px, 2.8vmin, 36px);
  --control-size: clamp(48px, 7vmin, 88px);
}

html[data-ui-mode="mobile"] {
  --text-size: clamp(16px, 3.8vw, 22px);
  --hud-size: clamp(18px, 4.8vw, 28px);
  --control-size: clamp(48px, 13vw, 68px);
}

html[data-ui-mode="tv"] {
  --text-size: clamp(24px, 2.2vmin, 40px);
  --hud-size: clamp(28px, 3vmin, 52px);
  --control-size: clamp(72px, 7vmin, 120px);
}
```

Автоматический режим рекомендуется определять по области просмотра в CSS-пикселях и типу указателя. Телефон и планшет с `pointer: coarse` используют `mobile`. Большой сенсорный экран не менее примерно `1700 × 1000` CSS-пикселей может использовать `tv`. Для большого экрана с мышью автоматический `tv` рекомендуется только от примерно `2200 × 1300` CSS-пикселей. Эти пороги являются начальными ориентирами, а явно переданный `ui` всегда имеет приоритет.

Общие требования:
- запрещено уменьшать текст и зоны нажатия ниже установленных минимумов;
- запрещено масштабировать весь UI только через `transform: scale(...)`;
- базовые размеры визуальных игровых объектов должны быть заданы централизованно;
- игровые координаты и UI должны корректно пересчитываться после `resize` и изменения ориентации;
- запрещено ограничивать основной игровой контейнер жёстким `max-width` / `max-height`, если это делает игру визуально слишком мелкой;
- итоговый интерфейс должен сохранять читаемость и удобство на телефоне, планшете, компьютере и большом экране.

Если конкретная игра изначально проектируется под горизонтальную ориентацию, базовый макет и формула игрового мира могут быть изменены в её отдельном задании, но разделение масштаба игрового мира и читаемого UI сохраняется.

## 🖼 Canvas и разрешение

Если игра использует `<canvas>`:
- визуальный размер canvas должен соответствовать доступной области;
- внутреннее разрешение canvas должно учитывать `devicePixelRatio`, если это необходимо для чёткости;
- логические координаты игры не должны напрямую зависеть от физического количества пикселей экрана;
- после `resize` необходимо корректно пересчитать размеры и масштаб;
- изменение размеров canvas не должно ломать игровой мир и управление.

## 💡 Рекомендации для игр с непрерывным управлением

### 📱 Расположение элементов управления

Элементы управления не должны располагаться только в верхней или самой нижней части экрана, если это делает их неудобными для касания.

Рекомендуется размещать элементы управления:
- в центральной части экрана;
- справа или слева от центра;
- либо по центру, если это не мешает игровому процессу.

### 🎛 Группировка и перемещение

Элементы управления должны быть сгруппированы компактно.

При необходимости допускается перемещаемая панель управления:
- панель имеет понятную область для перетаскивания;
- пользователь может переместить её в удобное место;
- drag панели не должен запускать игровую механику.

### 🕹 Тип управления

Для непрерывного управления направлением рекомендуется использовать круговой virtual joystick или иной аналоговый контрол, а не четыре разнесённые кнопки.

Круговой контрол:
- задаёт направление движением пальца/указателя;
- поддерживает непрерывное направление;
- работает мышью и touch;
- если направление движения естественно управляется с клавиатуры, параллельно поддерживаются `WASD` и/или стрелки как альтернативный канал;
- корректно завершается при `pointercancel` / `touchcancel`;
- не создаёт двойной ввод.

### ✅ Допустимые исключения

Отдельные кнопки допустимы, если:
- управление дискретное;
- механика использует выбор, прыжок, действие или другую отдельную команду;
- непрерывное направление движения не требуется.

## 🚫 Общие анти-паттерны

Следующие подходы считаются ошибками проектирования и должны избегаться.

### ❌ Управление и UX

- элементы управления только в неудобной верхней зоне;
- элементы управления у самого нижнего края экрана;
- мелкие кнопки, по которым сложно попасть пальцем;
- разнесённые по экрану управляющие кнопки без необходимости;
- отсутствие визуальной обратной связи при нажатии;
- обязательный стартовый экран, который ничего не добавляет к механике;
- длинное описание перед началом игры;
- искусственная задержка перед стартом;
- непонятная игровая цель;
- необходимость скролла во время игры.

### ❌ Игровой процесс

- длительное ожидание без действий;
- чрезмерно длинный раунд без причины;
- изменение скорости игры при изменении FPS;
- зависимость движения от частоты экрана;
- таймер, считающий кадры вместо реального времени;
- запуск нескольких игровых циклов после повторных игр;
- старые объекты предыдущего раунда продолжают влиять на новый.

### ❌ Завершение и повтор

- игра продолжает менять счёт после финального состояния;
- отсутствует визуальный сигнал окончания раунда;
- отсутствует кнопка `Играть ещё раз`;
- повтор требует перезагрузки страницы;
- повтор не сбрасывает счёт или таймер;
- повтор не сбрасывает позиции и состояния объектов;
- после повтора остаются старые `setInterval` / `setTimeout`;
- после повтора появляется двойной `requestAnimationFrame` loop;
- обработчики событий повторно навешиваются и вызываются несколько раз;
- финальная кнопка запускает одновременно restart и игровое действие.

### ❌ Технические ошибки

- блокирующие операции и зависания;
- фиксированный layout, не адаптированный под целевой экран;
- элементы выходят за пределы экрана;
- отсутствие единой системы масштабирования UI и игровых объектов;
- интерфейс визуально уменьшается на больших экранах из-за неправильного ограничения размеров;
- декоративные элементы выглядят как прогрессбары, но не отражают реальное значение;
- избыточные текстовые тени и обводки ухудшают читаемость;
- скорость движения зависит от FPS или производительности устройства;
- одинаковая относительная дистанция проходится за разное время при смене разрешения;
- появляется системное меню при долгом нажатии;
- текст случайно выделяется во время игры;
- появляется браузерная лупа или системное touch-меню в игровом интерфейсе.

### ❌ Обработка событий

- отсутствие проверки `event.target` в игровых обработчиках;
- отсутствие проверки родителей цели события через `closest(...)`;
- игровые обработчики реагируют на нажатия по UI;
- UI не предотвращает передачу события в игровую механику;
- глобальные обработчики работают без фильтрации UI;
- используется только `click` там, где требуется мгновенная реакция, удержание или drag;
- одновременно без защиты используются Pointer Events, Touch Events и Mouse Events;
- одно физическое касание порождает несколько игровых действий;
- отсутствует обработка `pointercancel` или fallback-эквивалента;
- клавиатурное движение зависит от частоты автоповтора `keydown` вместо состояния нажатых клавиш;
- одноразовое действие многократно срабатывает из-за `event.repeat` без намеренной игровой причины;
- зажатая клавиша остаётся активной после `blur`, скрытия вкладки, завершения или рестарта;
- глобальный `keydown` запускает игровое действие, когда фокус находится на кнопке, поле ввода или другом UI;
- `Arrow*` или `Space` прокручивают страницу во время активного игрового управления;
- `pointer-events: none` блокирует интерактивный UI;
- отсутствует приоритет UI над игровым слоем.

### ❌ Несовместимость устройств

- игра работает только мышью;
- игра работает только touch;
- игра работает только клавиатурой;
- механика допускает клавиатурное управление, но на компьютере оно отсутствует;
- игра работает на смартфоне, но не работает на интерактивном экране;
- игра работает на интерактивном экране, но не работает на компьютере;
- drag, multitouch, joystick или быстрые касания работают только на части устройств;
- UI можно нажать мышью, но нельзя пальцем;
- игровые действия работают пальцем, но не работают мышью;
- клавиатурные действия конфликтуют с кнопками и другими элементами UI.

## 🧹 Защита от системного поведения браузера

Для игрового интерфейса рекомендуется отключить поведение, мешающее touch-взаимодействию:

```css
html, body, #gameRoot {
  margin: 0;
  width: 100%;
  height: 100%;
  overflow: hidden;
  touch-action: none;
  user-select: none;
  -webkit-user-select: none;
  -webkit-touch-callout: none;
}
```

При необходимости следует дополнительно предотвращать `contextmenu` внутри игровой области.

При этом нельзя ломать доступность и ввод в элементах, которым действительно требуется текстовый ввод, если такие элементы предусмотрены заданием.

## 🧩 ШАБЛОН ДЛЯ AI

### 📦 Формат ответа для AI-генерации

Если игра генерируется через ИИ, ответ должен соответствовать следующим требованиям:

- ответ должен быть возвращён только в виде полного HTML-кода, если запрошен готовый HTML;
- каждая отдельная игра должна быть возвращена как один самостоятельный HTML-файл;
- весь CSS и JavaScript должны быть встроены в тот же HTML-файл;
- один HTML-файл не должен содержать несколько разных самостоятельных игр;
- код должен быть аккуратным, структурированным и пригодным для редактирования;
- не допускается разбивать одну игру на несколько файлов;
- не допускается добавлять пояснительный текст вне кода, если запрошен готовый HTML-файл;
- игра не должна добавлять внешние интеграционные протоколы или сетевой обмен, если это отдельно не запрошено;
- игра должна стартовать локально и самостоятельно;
- игра обязана читать `?diff=1..5`, использовать `3` по умолчанию и реально применять сложность к механике;
- игра должна принимать `?ui=mobile` и `?ui=tv`, а без корректного значения автоматически выбирать читаемый режим;
- игра должна корректно работать как top-level страница и при загрузке во `iframe`;
- если предусмотрена кнопка `Завершить игру` / `Выйти`, top-level режим использует возврат по истории, а iframe-режим отправляет родителю `{ type: 'gameExit' }`;
- финальный экран должен содержать кнопку `Играть ещё раз`;
- повтор должен полностью сбрасывать раунд без `location.reload()`.

Важно для AI-генерации:
- Pointer Events должны использоваться как основной канал pointer/touch-ввода, если они доступны;
- Touch Events и Mouse Events не должны безусловно навешиваться параллельно на ту же игровую механику;
- fallback для mouse/touch должен включаться только при отсутствии Pointer Events либо при наличии явной дедупликации;
- одно физическое касание или клик не должны проходить в игровую логику несколько раз;
- если механика допускает управление клавишами, AI обязан реализовать keyboard-ввод как дополнительный канал, сохраняя полноценные mouse/touch-контролы;
- для движения рекомендуется поддерживать `WASD` и стрелки, для дискретного действия — `Space` и/или `Enter`, когда это подходит механике;
- клавиатурное удержание должно реализовываться через состояние `keydown` / `keyup`, а не через частоту автоповтора;
- состояние нажатых клавиш должно очищаться при `blur`, скрытии документа, завершении и рестарте игры;
- глобальные keyboard-обработчики должны игнорировать поля ввода и интерактивный UI;
- повтор игры не должен создавать дублирующиеся animation loop или обработчики.

function applyScale() {
  const viewportWidth = window.visualViewport?.width || window.innerWidth;
  const viewportHeight = window.visualViewport?.height || window.innerHeight;
  const shortSide = Math.min(viewportWidth, viewportHeight);
  const longSide = Math.max(viewportWidth, viewportHeight);
  const coarsePointer = window.matchMedia?.('(pointer: coarse)').matches === true;
  const automaticMode = coarsePointer && shortSide >= 1000 && longSide >= 1700
    ? 'tv'

      ? 'tv'
      : coarsePointer || shortSide < 700

        : 'auto';

  document.documentElement.dataset.uiMode = uiMode;
  document.documentElement.style.setProperty('--world-scale', worldScale.toFixed(5));
  resizeCanvas();
}

function resizeCanvas() {
  const dpr = Math.max(1, window.devicePixelRatio || 1);
  const rect = gameRoot.getBoundingClientRect();

  canvas.width = Math.max(1, Math.round(rect.width * dpr));
  canvas.height = Math.max(1, Math.round(rect.height * dpr));
  canvas.style.width = `${rect.width}px`;
  canvas.style.height = `${rect.height}px`;

  ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
}

function isUiTarget(target) {
  return !!(
    target &&
    target.closest('.button, .panel, .overlay, .ui-control, [data-ui="true"]')
  );
}

function isEditableTarget(target) {
  return !!(
    target &&
    target.closest('input, textarea, select, [contenteditable="true"]')

}

function isGameKey(code) {
  return [
    'ArrowUp', 'ArrowDown', 'ArrowLeft', 'ArrowRight',
    'KeyW', 'KeyA', 'KeyS', 'KeyD',
    'Space', 'Enter'
  ].includes(code);
}

function clearKeyboardState() {
  pressedKeys.clear();
}

function resetRoundState() {
  state.gameActive = true;
  state.finished = false;
  state.score = 0;
  state.timeLeft = CONFIG.roundTime;
  state.objects.length = 0;

  mouseActive = false;
  activePointerId = null;
  clearKeyboardState();

  // бонусы, эффекты и другие данные конкретной игры.
}

function startNewRound() {
  resetRoundState();

}

function endGame({ success = false, text = '' } = {}) {
  if (state.finished) return;

  state.gameActive = false;
  state.finished = true;

  mouseActive = false;
  activePointerId = null;
  clearKeyboardState();

  finishTitle.textContent = success ? 'Победа!' : 'Раунд завершён';
  finishValue.textContent = text || `Счёт: ${state.score}`;
  finishOverlay.classList.remove('hidden');

function update(dt) {
  if (!state.gameActive) return;

  state.timeLeft = Math.max(0, state.timeLeft - dt);

  // Пример непрерывного клавиатурного направления.
  // Движение должно рассчитываться через dt, а не через частоту keydown.
  const moveX =
    (pressedKeys.has('ArrowRight') || pressedKeys.has('KeyD') ? 1 : 0) -
    (pressedKeys.has('ArrowLeft') || pressedKeys.has('KeyA') ? 1 : 0);
  const moveY =
    (pressedKeys.has('ArrowDown') || pressedKeys.has('KeyS') ? 1 : 0) -
    (pressedKeys.has('ArrowUp') || pressedKeys.has('KeyW') ? 1 : 0);

  // игровая логика; например:
  // player.x += moveX * CONFIG.playerSpeed * dt;
  // player.y += moveY * CONFIG.playerSpeed * dt;

  if (state.timeLeft <= 0) {
    endGame({
      success: state.score >= CONFIG.targetScore,
      text: `Счёт: ${state.score}`
    });
  }
}

  if (isUiTarget(event.target)) return;
  if (event.cancelable) event.preventDefault();

}

  if (isUiTarget(event.target)) return;

}

function onGameInputEnd(event) {
  if (event && event.cancelable) event.preventDefault();
  tryReleasePointer(event);

  // игровая логика завершения ввода
}

function tryCapturePointer(event) {
  if (!HAS_POINTER_EVENTS) return;
  if (!event || event.pointerId == null) return;
  if (!event.target || !event.target.setPointerCapture) return;

  try {
    event.target.setPointerCapture(event.pointerId);
    activePointerId = event.pointerId;
  } catch (_) {}
}

function tryReleasePointer(event) {
  if (!HAS_POINTER_EVENTS) return;
  if (!event || event.pointerId == null) return;

  try {
    if (
      event.target &&
      event.target.releasePointerCapture &&
      event.target.hasPointerCapture &&
      event.target.hasPointerCapture(event.pointerId)
    ) {
      event.target.releasePointerCapture(event.pointerId);
    }
  } catch (_) {}

  if (activePointerId === event.pointerId) {
    activePointerId = null;
  }
}

function bindUiButton(button, handler) {
  const stop = (event) => {
    if (event.cancelable) event.preventDefault();
    event.stopPropagation();
  };

  ['pointerdown', 'pointerup', 'touchstart', 'touchend', 'mousedown', 'mouseup']
    .forEach(type => button.addEventListener(type, stop, { passive: false }));

  button.addEventListener('click', (event) => {
    stop(event);
    handler();
  });
}

function exitGame() {
  state.gameActive = false;
  mouseActive = false;
  activePointerId = null;
  clearKeyboardState();

  if (window.self !== window.top) {
    // Родитель сам решает: закрыть iframe, показать каталог или перейти назад.
    window.parent.postMessage({ type: 'gameExit' }, '*');
    return;

  if (window.history.length > 1) {
    window.history.back();
    return;

  // адреса возврата нет, поэтому остаёмся на странице игры.
  exitButton.disabled = true;
  exitButton.textContent = 'Нет страницы для возврата';
}

    if (!state.gameActive) return;
    if (isEditableTarget(event.target) || isUiTarget(event.target)) return;

    if (event.cancelable) event.preventDefault();

    // Для непрерывного движения храним состояние клавиш.
    pressedKeys.add(event.code);

    // Пример одноразового действия без браузерного автоповтора.
    if (!event.repeat && (event.code === 'Space' || event.code === 'Enter')) {
      // игровая логика основного действия
    }
  }, { passive: false });

  window.addEventListener('keyup', (event) => {
    if (!isGameKey(event.code)) return;
    pressedKeys.delete(event.code);

    if (state.gameActive && !isEditableTarget(event.target) && !isUiTarget(event.target)) {
      if (event.cancelable) event.preventDefault();
    }
  }, { passive: false });

  window.addEventListener('blur', clearKeyboardState);
  document.addEventListener('visibilitychange', () => {
    if (document.hidden) clearKeyboardState();
  });
}

function bindInput() {
  if (HAS_POINTER_EVENTS) {
    gameRoot.addEventListener('pointerdown', (event) => {
      onGameInputStart(event, event.clientX, event.clientY);
    }, { passive: false });

    gameRoot.addEventListener('pointermove', (event) => {
      onGameInputMove(event, event.clientX, event.clientY);
    }, { passive: false });

    gameRoot.addEventListener('pointerup', (event) => {
      onGameInputEnd(event);
    }, { passive: false });

    gameRoot.addEventListener('pointercancel', (event) => {
      onGameInputEnd(event);
    }, { passive: false });

    return;
  }

  gameRoot.addEventListener('mousedown', (event) => {
    if (isUiTarget(event.target)) return;
    mouseActive = true;
    onGameInputStart(event, event.clientX, event.clientY);
  }, { passive: false });

  window.addEventListener('mousemove', (event) => {
    if (!mouseActive) return;
    onGameInputMove(event, event.clientX, event.clientY);
  }, { passive: false });

  window.addEventListener('mouseup', (event) => {
    if (!mouseActive) return;
    mouseActive = false;
    onGameInputEnd(event);
  }, { passive: false });

  gameRoot.addEventListener('touchstart', (event) => {
    if (isUiTarget(event.target)) {
      if (event.cancelable) event.preventDefault();
      return;
    }

    for (const touch of event.changedTouches) {
      onGameInputStart(event, touch.clientX, touch.clientY);
    }
  }, { passive: false });

  gameRoot.addEventListener('touchmove', (event) => {
    if (isUiTarget(event.target)) {
      if (event.cancelable) event.preventDefault();
      return;
    }

    for (const touch of event.changedTouches) {
      onGameInputMove(event, touch.clientX, touch.clientY);
    }
  }, { passive: false });

  gameRoot.addEventListener('touchend', (event) => {
    onGameInputEnd(event);
  }, { passive: false });

  gameRoot.addEventListener('touchcancel', (event) => {
    onGameInputEnd(event);
  }, { passive: false });
}

window.addEventListener('contextmenu', (event) => {
  if (gameRoot.contains(event.target)) event.preventDefault();
});

window.addEventListener('resize', applyScale);

bindUiButton(restartButton, startNewRound);
bindUiButton(exitButton, exitGame);
bindInput();
bindKeyboard();
applyScale();
startNewRound();
requestAnimationFrame(frame);
</script>
</body>

### Важные принципы шаблона

`CONFIG.difficulty` читается из `?diff=` один раз при загрузке. Значение должно использоваться конкретной игровой механикой при расчёте параметров раунда.

`CONFIG.uiMode` читает только `ui=mobile` или `ui=tv`. При отсутствии корректного значения `applyScale()` автоматически выбирает режим и пересчитывает его после `resize`. Масштаб игрового мира не уменьшает текст или зоны нажатия ниже установленных CSS-минимумов.

Кнопка `Завершить игру` работает без прямого управления родителем: при запуске во `iframe` она отправляет только `gameExit`, а при обычном открытии использует `history.back()` при наличии предыдущей записи.

Animation loop создаётся только один раз:

```js
requestAnimationFrame(frame);
```

При повторе игры функция `startNewRound()` только сбрасывает состояние.
Она не создаёт ещё один `requestAnimationFrame(frame)`.

Это предотвращает ускорение игры и дублирование логики после нескольких повторов.

## ✅ Минимальный чек-лист совместимости

Игра соответствует спецификации, если она:

- находится в отдельном HTML-файле: один файл = одна игра;
- весь CSS и JavaScript игры находятся в этом же HTML-файле;
- не требует обязательного внешнего игрового движка или сервиса;
- запускается самостоятельно;
- корректно запускается как обычная страница и внутри `iframe`;
- читает сложность из `?diff=1..5`;
- использует `diff=3` как среднюю сложность и значение по умолчанию;
- при некорректном `diff` использует `3`;
- реально применяет выбранную сложность к игровой механике;
- принимает `?ui=mobile` и `?ui=tv`, игнорирует другие значения и сохраняет читаемость в автоматическом режиме;
- если есть кнопка выхода, в top-level режиме возвращается через историю, а во `iframe` отправляет родителю `gameExit`;
- не требует отдельного стартового экрана с описанием;
- начинает раунд без искусственной задержки;
- работает без обязательного интернета;
- поддерживает mouse и touch;
- поддерживает keyboard-ввод на компьютере для механик, которые естественно управляются клавишами;
- не делает клавиатуру единственным способом прохождения игры;
- для движения с клавиатуры использует состояние `keydown` / `keyup`, а не частоту автоповтора;
- очищает состояние зажатых клавиш при `blur`, скрытии документа, завершении и рестарте;
- не запускает игровую keyboard-логику из полей ввода или интерактивного UI;
- корректно работает на интерактивном экране;
- использует Pointer Events как основной канал pointer/touch-ввода, если они доступны;
- не допускает двойной обработки одного физического pointer/touch-ввода;
- обрабатывает отмену pointer/touch-ввода;
- не зависит от FPS в логике движения и времени;
- раздельно масштабирует игровой мир и UI, не уменьшая текст и зоны касания ниже установленных минимумов;
- не требует скролла;
- не допускает системных touch-меню и случайного выделения текста в игровой области;
- корректно завершает текущий раунд;
- после завершения больше не изменяет результат;
- показывает понятный финальный статус;
- содержит кнопку `Играть ещё раз`;
- повтор полностью сбрасывает состояние;
- повтор не перезагружает страницу;
- повтор не создаёт дублирующиеся таймеры, циклы или обработчики событий;
- после нескольких повторов игра работает с той же скоростью и тем же поведением, что и после первой загрузки.

# 🏁 ИТОГ

Совместимая игра должна:
- быть автономной и находиться в отдельном HTML-файле;
- запускаться сразу после локальной инициализации;
- принимать сложность из `?diff=1..5`, используя `3` как среднее значение по умолчанию;
- принимать подсказки `?ui=mobile` и `?ui=tv`, сохраняя автоматический режим при их отсутствии;
- корректно работать как самостоятельная страница и внутри `iframe`;
- поддерживать безопасный возврат: через историю в top-level режиме и через `gameExit` при запуске во `iframe`;
- самостоятельно управлять своим состоянием, запуском и завершением раунда;
- корректно работать с mouse, touch и интерактивными экранами, а на компьютере также поддерживать keyboard-ввод для механик, которые естественно управляются клавишами;
- раздельно масштабировать игровой мир и читаемый пользовательский интерфейс;
- не зависеть от FPS и производительности устройства там, где важна временная логика;
- корректно останавливать завершённый раунд;
- показывать понятный итог;
- обязательно давать возможность сыграть ещё раз;
- выполнять повтор через полный сброс локального состояния без перезагрузки HTML-документа.

Этот файл можно использовать как:
- спецификацию для разработчика;
- чек-лист проверки автономной игры;
- промпт для генерации игр через ИИ.
