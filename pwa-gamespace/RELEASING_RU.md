# Выпуск GameSpace

## Модель версий

APK и PWA используют единый номер выпуска. Тег GitHub Release является
единственным источником версии для автоматической сборки. Нулевые компоненты в
конце тега опускаются: `v1` означает техническую версию `1.0.0`, `v0.5` —
`0.5.0`, а `v0.6.22` остаётся `0.6.22`. В интерфейсе и технических метаданных
приложений используется нормализованный номер из трёх компонентов. При ненулевом
`PATCH` нулевой `MINOR` сохраняется: `v1.0.1`, `v0.0.1`.

Каждый PWA-выпуск хранится как asset соответствующего GitHub Release с именем
`gamespace-pwa-<версия>.tar.gz`, а подписанный APK — как
`GameSpace-<версия>.apk`. Тот же подписанный APK дополнительно прикрепляется под
именем `GameSpace-latest.apk`, чтобы постоянная ссылка через `releases/latest`
вела непосредственно на файл актуального стабильного выпуска. Это копия, а не
отдельная версия или тег. Опубликованные assets не перезаписываются.
Release workflow извлекает их во временный `release-packages/<версия>/`,
копирует последнюю проверенную общую версию в корень GitHub Pages, а историю
PWA оставляет на сайте по путям вида `releases/0.3.0/`: три последние версии
обязательны, более старые добавляются по порядку до десяти, пока хватает места.
Более старые архивы и APK остаются в GitHub Releases.

После публикации `sw-runtime-v1.js` является неизменяемой средой выполнения.
Его контрольная сумма зафиксирована в `runtime-lock.json`. Любое последующее
функциональное изменение требует нового имени, например `sw-runtime-v2.js`,
отдельной проверки миграции и явного согласия пользователя на установку.

В меню кнопка **Проверить обновление программы** после обнаружения нового выпуска
меняется на **Обновить до версии X**. Карточки показываются по одной, начиная с
последней; **Предыдущая версия** заменяет карточку, **К последней версии** возвращает
начало. Описание свёрнуто и находится над установкой. Локальный откат доступен
в **Программе → Восстановление и сведения о браузере**, включая работу без сети.

Приложение не проверяет каталог версий при обычном запуске. Сетевой запрос за
`versions.json` и загрузка выбранного выпуска выполняются только после явного
действия пользователя. Браузер всё равно вправе выполнить стандартную
техническую проверку URL зарегистрированного Service Worker; опубликованный
файл по этому URL остаётся байт-в-байт неизменным и сам не загружает новый
выпуск.

## Подготовка нового выпуска

Пример для единого выпуска `0.4.0` с тегом `v0.4`:

1. Не изменять номера версии вручную в файлах PWA и APK: при публикации Release
   workflow получит версию из тега `v0.4` и применит `0.4.0` к обеим сборкам.
2. Выполнить локальные проверки из каталога `pwa-gamespace/`. `demo.7z` будет
   каждый раз создан из `demo/`:

   ```powershell
   npm install
   npm test
   npx playwright install chromium
   npm run test:e2e
   npm run verify:runtime
   ```

3. При необходимости проверить локальную APK-сборку с будущей версией:

   ```bat
   apk-gamespace\build-apk.bat build 0.4.0
   ```

4. После отправки коммита дождаться успешного workflow
   **Проверка каждого коммита**. Он повторяет сборку PWA на Linux, создаёт
   тестовый Pages-артефакт и собирает APK с отдельной тестовой подписью на
   Windows. В задании APK также проверяется каталог обновлений, в том числе
   настоящими SDK-инструментами на тестовом APK. Workflow ничего не публикует
   и не использует релизный ключ.
5. Пользователь самостоятельно добавляет файлы в Git, создаёт commit и тег
   `v0.4`, отправляет их в GitHub и публикует стабильный GitHub Release с этим
   тегом кнопкой **Publish release**.
6. Событие публикации автоматически запускает **Publish GameSpace release**.
   Workflow получает `0.4.0` из тега, синхронизирует метаданные PWA, вычисляет
   Android `versionCode` и параллельно собирает оба приложения. Только после
   успешных проверок он прикрепляет готовые файлы к опубликованному Release,
   проверяет их повторным скачиванием и обновляет GitHub Pages.

## Что делает GitHub Actions

Workflow `.github/workflows/publish-pwa-pages.yml` автоматически запускается по
событию `release: published`. Он принимает только опубликованный стабильный
Release без признака prerelease и канонический тег `vMAJOR`, `vMAJOR.MINOR`
или `vMAJOR.MINOR.PATCH`. Нулевой `PATCH` опускается, а если `MINOR` также равен
нулю, опускаются оба компонента. Поэтому используются `v1`, `v0.5` и
`v0.6.22`, но не `v1.0`, `v0.5.0` или версия из четырёх чисел.

PWA и подписанный APK проверяются в независимых заданиях. Браузерные сценарии
также запускаются параллельно в трёх заданиях: `interface` (интерфейс и архивы),
`runtime` (обновление, откат и восстановление оболочки) и `fps` (показания FPS).
Каждое задание имеет собственный runner, тестовый сервер и один браузерный
worker. Публикация файлов ожидает успешного завершения всех трёх групп, сборки
PWA и проверки APK. При ошибке сохраняются скриншоты и trace на семь дней.
Те же группы используются в непубликующем workflow каждого коммита и PR;
локальный `npm run test:e2e` по-прежнему выполняет весь набор. Отдельную группу
можно запустить командой `npm run test:e2e -- --project=runtime`.

Опубликованные файлы
не перезаписываются: при повторном запуске PWA-пакет скачивается и сверяется с
исходной сборкой, а существующий APK проверяется по подписи, сертификату, имени
пакета и версии относительно новой сборки того же тега. Версионный APK и
`GameSpace-latest.apk` должны совпадать побайтно. Недостающие файлы добавляются
после успешных проверок обеих программ. Выпуски, в которых ещё нет PWA-пакета,
пропускаются при восстановлении каталога прошлых версий.
Workflow:

1. проверяет тег и применяет его номер к PWA и APK;
2. устанавливает версии зависимостей из `package-lock.json`;
3. создаёт `demo.7z` из файлов `demo/`, тестирует архив и собирает PWA;
4. просматривает до 100 стабильных релизов и текущий тег, сортирует их по номеру
   версии и загружает до десяти последних доступных PWA-пакетов; старый текущий
   тег дополнительно загружается для проверки точных опубликованных байтов;
5. создаёт новый неизменяемый пакет текущего Release или проверяет существующий;
6. включает `LICENSE.txt`, `BRAND_ASSETS_LICENSE.md`,
   `DEMO_CONTENT_LICENSE.md`, `THIRD_PARTY_NOTICES.md`, полные тексты
   сторонних лицензий и необходимые исходники LGPL-компонента;
7. проверяет неизменяемый runtime, контрольные суммы и совпадение сборки с тегом;
8. собирает подписанный APK тем же номером версии, фиксирует отпечаток его
   сертификата и готовит версионный файл и идентичную копию `GameSpace-latest.apk`;
9. после успешной подготовки обеих программ прикрепляет недостающие файлы к
   Release: версионный PWA-пакет, версионный APK и `GameSpace-latest.apk`, затем
   скачивает все три файла и проверяет их побайтное совпадение с подготовленными;
10. в отдельном задании `pages` восстанавливает каталог APK из готовых файлов
    стабильных релизов: сверяет обе копии APK, подпись, версию, размер и SHA-256
    либо повторно использует подходящие проверенные сведения, как описано ниже;
11. повторно проверяет переданные PWA-пакеты, выбирает наибольшую проверенную
    общую версию, собирает Pages и добавляет `apk/updates.json` вне неизменяемых
    PWA-пакетов, выбирает от трёх до десяти последних PWA-выпусков по размеру
    и проверяет общий размер;
    только после этого задание `deploy` развёртывает сайт.

Каталог APK восстанавливается из последних 100 стабильных GitHub Releases
и текущего тега. Прежний JSON на Pages служит необязательным кэшем: сведения
используются повторно только при совпадении SHA-256 и размера обеих копий APK
с текущими метаданными GitHub, даты публикации и ожидаемого сертификата.
Описания обновляются из Releases. Без кэша, при его ошибке или при отсутствии
`digest` у любого из двух APK файлы скачиваются и проверяются через SDK.
Для записи нужны готовые версионный APK, его копия `GameSpace-latest.apk`
и PWA-пакет. Отпечаток ожидаемого сертификата приходит из задания сборки APK,
а не из скачанного каталога. Ошибка проверки любого готового APK останавливает
публикацию. Дополнительных секретов для каталога нет.

Повтор старого релиза не назначает его последним, если среди восстановленных
готовых релизов есть более новая версия. В корне Pages используется PWA той же
последней версии; файлы сохраняемых `releases/<версия>/` и опубликованные
runtime не меняются. Каталоги за пределами выбранной истории не включаются
в новый Pages-артефакт, в том числе при повторном запуске старого тега.
При сбое задания `pages` развёртывание не запускается и прежний сайт сохраняется.
Подробности каталога и этапов внедрения кнопок APK:
[`APP_UPDATES_RU.md`](../apk-gamespace/APP_UPDATES_RU.md).

Release становится публичным сразу после нажатия **Publish release**; файлы
появляются после сборки. При ошибке проверки или сборки новые файлы не
прикрепляются и GitHub Pages не обновляется. Если сбой произошёл уже при загрузке
файлов, повторный запуск проверит загруженные файлы и добавит недостающие.

После ошибки можно использовать **Re-run all jobs**. Для опубликованного
Release, у которого запуск вообще не появился, предусмотрен дополнительный
ручной запуск: **Actions → Publish GameSpace release → Run workflow**.
В списке **Use workflow from → Tags** выбрать тег выпуска; в поле `tag`
указать тот же канонический тег. Окружение `github-pages` допускает только
теги `v*`: выбор `main` приведёт к отказу финального деплоя. Сборки
берутся из указанного тега. Этот способ также подходит для `v0.3.13`, созданного
до восстановления автоматического запуска, если в выбранном теге уже есть
ручной trigger. Исправленный workflow должен быть
отправлен в `main`; для последующих автоматических запусков он должен входить
и в коммит нового тега. Само обновление workflow не запускает старые релизы
задним числом. Новые инструменты финальной сборки Pages и каталога APK берутся
из коммита запускаемого workflow (`github.workflow_sha`); исходники обеих
программ для сборки по-прежнему берутся из указанного релизного тега.

Ранее опубликованные неизменяемые пакеты проверяются по составу и контрольным
суммам их собственных манифестов. Маркер полного лицензионного комплекта
добавляется в новые выпуски и не применяется задним числом к старым пакетам.

## Быстрый деплой готового релиза

Workflow **Deploy published GameSpace release** (`deploy-published-release.yml`)
восстанавливает сайт из уже опубликованных пакетов без сборки приложений,
браузерных тестов, доступа к закрытому ключу или перезаписи GitHub Releases.
Если готовых файлов нет, он останавливается; для первой публикации и
незавершённой загрузки файлов нужен обычный **Publish GameSpace release**.

Один раз создать repository variable **APK_SIGNER_SHA256** в **Settings →
Secrets and variables → Actions → Variables**. Значение — доверенный SHA-256
сертификата существующего релизного APK: 64 шестнадцатеричных символа без
двоеточий. Это публичный отпечаток, не пароль и не закрытый ключ. В обычном
release workflow он выводится в summary после проверки подписанной сборки.
Отпечаток следует брать из собственной сборки с известным релизным ключом,
а не из непроверенного файла или текста описания Release.

Запуск через сайт GitHub:

1. Открыть **Actions → Deploy published GameSpace release → Run workflow**.
2. В **Use workflow from → Tags** выбрать тег, содержащий этот новый workflow.
3. В поле `tag` указать опубликованный выпуск, чьи готовые файлы нужно проверить.
4. Запустить workflow. Оба процесса публикации используют общую очередь,
   поэтому они не разворачивают сайт одновременно.

Файл нового workflow должен сначала попасть в `main` и в новый релизный тег.
Для тега с инструментами достаточно отправить сам тег в репозиторий:
публиковать отдельный GitHub Release для него не обязательно. Опубликованный
стабильный Release с полным комплектом файлов требуется для поля `tag`.
В старых тегах, например `v0.3.26`, этого файла нет, поэтому выбрать их
источником нового workflow нельзя. После появления нового тега с инструментами
его можно выбрать в **Use workflow from**, а в поле `tag` указать `v0.3.26`.
Переносить старый тег и заменять опубликованные файлы не требуется.

Быстрый путь проверяет стабильный статус Release, пакет и версию APK, подпись
относительно `APK_SIGNER_SHA256`, совпадение двух копий APK, размеры и SHA-256.
Ранее проверенные сведения APK используются повторно только при совпадении
обеих контрольных сумм GitHub и доверенного сертификата; без подходящего кеша
выполняется полная SDK-проверка. Для PWA обязательно наличие SHA-256 GitHub:
архив проверяется до распаковки, ссылки и небезопасные пути отклоняются,
после распаковки сверяются все файлы, манифест, лицензии и неизменяемый runtime.

Для Pages выбирается наибольшая готовая общая версия из проверенного каталога.
Запрос старого тега не понижает версию сайта. История PWA, предел размера Pages
и правило неизменяемых пакетов сохраняются. Ошибка проверки не запускает деплой
и не меняет прежний сайт. Отсутствие SHA-256 в метаданных старого PWA-архива
также останавливает быстрый путь; такой выпуск требует отдельной проверки.

## Хранение истории и предел размера Pages

GitHub Releases остаётся архивом всех опубликованных выпусков. Workflow не
удаляет релизы, APK или PWA-архивы. На Pages обязательно включаются три последних
доступных PWA-выпуска из рассматриваемого окна стабильных релизов. Затем по
убыванию номера версии добавляются четвёртый, пятый и последующие — максимум
до десяти. Если очередной выпуск выводит общий размер за 900 000 000 байт,
он и все более старые выпуски не включаются. Пропуск большой версии ради более
старой маленькой не выполняется. Если выпусков пока один или два, берутся все.

При расчёте заранее учитываются дополнительная копия актуального выпуска
в корне, манифесты, лицензии, JSON-каталоги и `apk/updates.json`. Размеры берутся
из фактических файлов; текстовые метаданные считаются в байтах UTF-8.
`versions.json` перечисляет только пакеты, которые действительно входят в Pages.
Рабочая папка сборки может временно
содержать одиннадцатый пакет: новый или отдельно проверяемый старый текущий тег.
Это не расширяет набор версий готового сайта.

`scripts/verify-pages-size.mjs` считает байты всех файлов готового сайта,
включая корневую копию, `releases/`, лицензии и `apk/updates.json`.
Предел составляет **900 000 000 байт (900 МБ)**; точное равенство допускается.
Этот предел проекта оставляет запас до
[ограничения GitHub Pages в 1 ГБ](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).
В CI проверяется тестовый Pages-артефакт. В release workflow каталог APK
передаётся сборщику через `--apk-catalog`, чтобы его размер учитывался до выбора
истории. После сборки общий размер проверяется повторно, до загрузки артефакта.
Сборщик копирует только выбранные версии и не удаляет исходные пакеты.
Если даже обязательные три выпуска с корневой копией и метаданными превышают
предел, подготовка останавливается до создания нового Pages-артефакта.
История автоматически до двух версий не сокращается. Прежний опубликованный
сайт остаётся доступен, а новые файлы в GitHub Release сохраняются.

Установленная PWA хранит свою рабочую оболочку в локальном кэше по корневым
адресам. Исчезновение старого `releases/<версия>/` с сервера само по себе
не стирает приложение, импортированный сайт или сохранения. Ручная проверка
получает актуальный каталог, а выбранное обновление загружается из нового
каталога выпуска. Локальный возврат к сохранённой предыдущей версии не требует
старой серверной папки. Это предполагает сохранность данных браузера.
Свежая установка удалённого с Pages выпуска через каталог больше недоступна;
его исходный архив остаётся в GitHub Releases.

Браузерный сценарий `e2e/release-runtime.spec.js` собирает два состояния Pages,
устанавливает старую PWA, импортирует небольшой сайт и записывает сохранение,
закрывает браузер, переключает сервер на историю, сокращённую по размеру до трёх
новых версий, и проверяет 404
старого манифеста. Затем проверяются запуск из прежнего профиля, ручное обновление,
сохранность сайта и сохранения, автономный запуск и локальный откат.
Это тест Chromium на компьютере, а не подтверждение испытаний на Android/iOS.

## Подпись APK в GitHub Actions

Workflow никогда не создаёт новый ключ для релизного APK. После загрузки
репозитория, но до публикации первого Release с автоматической сборкой APK, в
GitHub Actions Secrets необходимо добавить существующий ключ APK и его
параметры:

- `GAMESPACE_APK_KEYSTORE_BASE64`;
- `GAMESPACE_APK_KEY_ALIAS`;
- `GAMESPACE_APK_KEYSTORE_PASSWORD`;
- `GAMESPACE_APK_KEY_PASSWORD`.

Эта настройка выполняется владельцем официального репозитория один раз и затем
используется для следующих выпусков. Владелец отдельного форка при необходимости
автоматической сборки APK настраивает собственный ключ и секреты.

Ключ восстанавливается только во временном каталоге GitHub runner и не входит в
репозиторий или assets выпуска. Если секрет отсутствует, сборка завершается
ошибкой вместо создания APK с новым несовместимым ключом. Порядок подготовки
секретов приведён в `apk-gamespace/README_APK.md`.

## Возврат и прошлая версия

Пользователь может явно выбрать прошлый выпуск в приложении. Перед активацией
нового выпуска сохраняется предыдущий; при неуспешном первом запуске выполняется
автоматический возврат. Ручной возврат доступен в меню и на встроенной странице
`__gamespace_recovery__/`.

Публикация более старого GitHub Release не должна использоваться для отката
всех пользователей: установленные PWA не обновляются автоматически. Для
исправления выпуска публикуется новая версия, а конкретный пользователь при
необходимости выбирает прежнюю версию вручную.
