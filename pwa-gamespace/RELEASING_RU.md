# Выпуск GameSpace

## Модель версий

APK и PWA используют единый номер выпуска. Тег GitHub Release является
единственным источником версии для автоматической сборки. Нулевые компоненты в
конце тега опускаются: `v1` означает техническую версию `1.0.0`, `v0.5` —
`0.5.0`, а `v0.6.22` остаётся `0.6.22`. В интерфейсе и технических метаданных
приложений используется нормализованный номер из трёх компонентов.

Каждый PWA-выпуск хранится как asset соответствующего GitHub Release с именем
`gamespace-pwa-<версия>.tar.gz`, а подписанный APK — как
`GameSpace-<версия>.apk`. Опубликованные assets не перезаписываются.
Release workflow извлекает их во временный `release-packages/<версия>/`,
копирует последнюю выбранную версию в корень GitHub Pages, а все выпуски
оставляет доступными на сайте по путям вида `releases/0.3.0/`.

После публикации `sw-runtime-v1.js` является неизменяемой средой выполнения.
Его контрольная сумма зафиксирована в `runtime-lock.json`. Любое последующее
функциональное изменение требует нового имени, например `sw-runtime-v2.js`,
отдельной проверки миграции и явного согласия пользователя на установку.

Приложение не проверяет каталог версий при обычном запуске. Сетевой запрос за
`versions.json` и загрузка выбранного выпуска выполняются только после явного
действия пользователя. Браузер всё равно вправе выполнить стандартную
техническую проверку URL зарегистрированного Service Worker; опубликованный
файл по этому URL остаётся байт-в-байт неизменным и сам не загружает новый
выпуск.

## Подготовка нового выпуска

Пример для единого выпуска `0.4.0` с тегом `v0.4`:

1. Не изменять номера версии вручную в файлах PWA и APK: при публикации Release
   workflow получит версию из тега `v0.4` и применит `0.4.0` к обеим сборкам.
2. Выполнить локальные проверки из каталога `pwa-gamespace/`. `demo.7z` будет
   каждый раз создан из `demo/`:

   ```powershell
   npm install
   npm test
   npm run verify:runtime
   ```

3. При необходимости проверить локальную APK-сборку с будущей версией:

   ```bat
   apk-gamespace\build-apk.bat build 0.4.0
   ```

4. Пользователь самостоятельно добавляет файлы в Git, создаёт commit и тег
   `v0.4`, отправляет их в GitHub и публикует стабильный GitHub Release.
5. Workflow получает `0.4.0` из тега, синхронизирует метаданные PWA, вычисляет
   Android `versionCode`, собирает оба приложения и прикрепляет их assets.
   Если asset уже существует, workflow не перезаписывает его.

## Что делает GitHub Actions

Workflow `.github/workflows/publish-pwa-pages.yml` запускается только событием
`release: published`. Дополнительно он принимает только стабильные релизы без
признака prerelease и канонические теги `vMAJOR`, `vMAJOR.MINOR` или
`vMAJOR.MINOR.PATCH`. Нулевой `PATCH` опускается, а если `MINOR` также равен
нулю, опускаются оба компонента. Поэтому используются `v1`, `v0.5` и
`v0.6.22`, но не `v1.0`, `v0.5.0` или версия из четырёх чисел.

Workflow создаёт новый пакет только при первом запуске для данного Release и
никогда не переписывает уже существующий asset. Он:

1. проверяет тег и применяет его номер к PWA и APK;
2. устанавливает версии зависимостей из `package-lock.json`;
3. создаёт `demo.7z` из файлов `demo/`, тестирует архив и собирает PWA;
4. загружает assets прошлых PWA-релизов;
5. создаёт новый пакет или проверяет уже существующий asset текущего Release;
6. включает `LICENSE`, `BRAND_ASSETS_LICENSE.md`, сторонние уведомления и
   необходимые исходники LGPL-компонентов;
7. проверяет неизменяемый runtime, контрольные суммы и совпадение сборки с тегом;
8. собирает подписанный APK тем же номером версии и прикрепляет его к Release;
9. собирает временный `pages-output/<версия>/` и публикует только этот
   Pages-артефакт после успешной подготовки обеих программ.

Если любая проверка не проходит, GitHub Pages не обновляется.

## Подпись APK в GitHub Actions

Workflow никогда не создаёт новый ключ для релизного APK. После загрузки
репозитория, но до публикации первого Release с автоматической сборкой APK, в
GitHub Actions Secrets необходимо добавить существующий ключ APK и его
параметры:

- `GAMESPACE_APK_KEYSTORE_BASE64`;
- `GAMESPACE_APK_KEY_ALIAS`;
- `GAMESPACE_APK_KEYSTORE_PASSWORD`;
- `GAMESPACE_APK_KEY_PASSWORD`.

Эта настройка выполняется владельцем официального репозитория один раз и затем
используется для следующих выпусков. Владелец отдельного форка при необходимости
автоматической сборки APK настраивает собственный ключ и секреты.

Ключ восстанавливается только во временном каталоге GitHub runner и не входит в
репозиторий или assets выпуска. Если секрет отсутствует, сборка завершается
ошибкой вместо создания APK с новым несовместимым ключом. Порядок подготовки
секретов приведён в `apk-gamespace/README_APK.md`.

## Возврат и прошлая версия

Пользователь может явно выбрать прошлый выпуск в приложении. Перед активацией
нового выпуска сохраняется предыдущий; при неуспешном первом запуске выполняется
автоматический возврат. Ручной возврат доступен в меню и на встроенной странице
`__gamespace_recovery__/`.

Публикация более старого GitHub Release не должна использоваться для отката
всех пользователей: установленные PWA не обновляются автоматически. Для
исправления выпуска публикуется новая версия, а конкретный пользователь при
необходимости выбирает прежнюю версию вручную.
