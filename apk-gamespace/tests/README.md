# Проверки GameSpace APK

## Каталог обновлений приложения

`apk-update-catalog.test.mjs` проверяет канонические теги и `versionCode`,
опубликованный статус релиза, ссылки и размер APK, SHA-256 файла и сертификата,
сохранение новой версии при повторе старого релиза, защиту опубликованного APK
от замены, ограничения JSON и сохранность входных файлов. Файлы с ошибками,
повреждённый предыдущий каталог и отказ SDK не должны давать готовый каталог.

Пути APK, переданные обоим инструментам SDK, сравниваются с `realpath` исходного
файла. Это учитывает различия регистра и короткие имена Windows (`RUNNER~1`),
которые могут присутствовать в `TEMP`/`TMP`. Простое строковое сравнение с
ненормализованным путём ошибочно отклоняло один и тот же файл. Отдельный сценарий
проверяет относительный путь и создаёт свой временный каталог внутри текущей
рабочей папки: на Windows системный `TEMP` может находиться на другом диске,
а относительный путь между дисками невозможен. Остальные сценарии продолжают
использовать системный временный каталог. Проверки байтов, размера и времени
изменения входного APK сохраняются; созданные тестовые каталоги удаляются.

Запуск из корня проекта, нужен Node.js 20+ без установки npm-зависимостей:

```cmd
node --test apk-gamespace/tests/apk-update-catalog.test.mjs apk-gamespace/tests/restore-update-catalog.test.mjs
```

Основные тесты используют подставные ответы SDK и не проверяют криптографию
Android. Дополнительный тест с настоящим SDK включается переменными окружения:

- `GAMESPACE_CATALOG_TEST_APK`: путь к уже собранному тестовому APK.
- `GAMESPACE_CATALOG_TEST_AAPT2`: путь к `aapt2.exe` на Windows или `aapt2` на Linux.
- `GAMESPACE_CATALOG_TEST_APKSIGNER_JAR`: путь к `build-tools/<version>/lib/apksigner.jar`.
- `GAMESPACE_CATALOG_TEST_JAVA`: путь к Java, необязательно при наличии Java в PATH.

После настройки переменных выполняется та же команда. Этот тест читает исходный
APK, создаёт каталог по локальным тестовым метаданным релиза, проверяет отказ
при неверном ожидаемом сертификате и при повреждении отдельной копии APK.
Размер, время изменения и SHA-256 исходного APK должны сохраниться. Временные
файлы размещаются в отдельном тестовом каталоге и удаляются после проверки.
Обращений к GitHub и публикации тестовых данных нет. Если переменная APK не
задана, SDK-тест явно пропускается; обычные тесты продолжают работать без SDK.

При сбое этого шага CI сохраняет TAP-журнал с названием теста, ошибкой и стеком
в сводке запуска Actions (Summary). Шаг продолжает завершаться ошибкой.

## Клиент обновлений APK — этап 3

строгий JSON/UTF-8, размеры и канонические версии, чужие URL, порядок выпусков,

Запуск из корня проекта:

powershell -NoProfile -ExecutionPolicy Bypass -File apk-gamespace/tests/test-diagnostics.ps1

Перед выпуском проверьте на отдельной тестовой установке Android 6 и Android 9+:

1. Обычный запуск APK и открытие «Обновление приложения» не обращаются к
   каталогу; запрос появляется только после нажатия кнопки. Двойное нажатие
   не создаёт параллельные запросы. Длинное описание и крупный шрифт прокручиваются.
2. Закрытие и повторное открытие окна во время проверки не теряют результат;
   перезапуск APK показывает сохранённую дату и сведения без нового запроса.
3. В авиарежиме после успешной проверки остаётся прежняя информация. До первой
   успешной проверки нет сообщения об актуальности. HTTP 404, плохой JSON и
   TLS-ошибка не должны заменять сохранённые данные.
4. Та же или более старая опубликованная версия не объявляется обновлением.
   Более высокий minSdk показывается как ограничение. Каталог описывает самый
   новый выпуск, а кнопка открывает его официальную страницу в браузере.
5. Демо и небольшой отдельный архив продолжают работать офлайн: изображения,
   аудио, Worker, сохранения, импорт и обновление сайта. Внешняя ссылка требует
   подтверждения; отмена оставляет игру открытой. Во время распаковки проверка
   обновлений отсутствует в меню.
6. Тестовые внешние HTTP/HTTPS, WebSocket и запросы Service Worker не загружаются
   внутри WebView. Нативная проверка каталога при этом работает. WebRTC проверяется
   отдельно: полной сетевой изоляции этот этап не обещает, см. [ограничения](../APP_UPDATES_RU.md).

Проверка физического устройства ещё не выполнена; успешных результатов для
нового экрана на конкретных версиях Android пока не заявляется.

## Переход на официальный выпуск

Проверки исходников и манифеста подтверждают, что приложение не запрашивает
`REQUEST_INSTALL_PACKAGES`, не содержит встроенного загрузчика или установщика
APK и открывает только `releaseUrl` проверенной записи каталога через браузер.
Описание выпуска должно находиться перед кнопкой перехода.

На устройстве нужно проверить открытие официальной страницы GitHub, возврат в
GameSpace и сохранность импортированного сайта. Скачивание и установка APK
проверяются отдельно как обычный системный сценарий Android вне приложения.

## Диагностика APK

`CompatibilityReportTest.java` проверяет текстовый контракт GS1 по тем же
эталонам из `docs/fixtures/compatibility-report-gs1.json`, что и PWA. Проверяются
успех, неполная проверка, ошибка, прерывание, неизвестные сведения, кавычки,
разделители, Unicode, большие размеры и хеш. Текст одинаков при четырёх локалях
JVM; лишние поля с путями и журналом в отчёт не попадают. Проверка включена
в `test-diagnostics.ps1` и существующий CI.

`CompatibilityCheckTest.java` проверяет сохранение наблюдений, неполный отчёт,
последовательность импорта и перехода из витрины, ошибки получения демо, страницы,
скрипта, ресурса и тайм-аута. Позднее событие загрузки не стирает ошибку; снимок
остаётся прежним до повторного формирования. Проверены смена версии, среды,
содержимого, прерванный импорт и отказ записи состояния. На устройстве отдельно
проверяются кнопка на пустом экране и во время импорта, автоматическое формирование
при повторном открытии, зелёные/жёлтые результаты шагов, копирование и открытие формы
даже при его отказе. Кнопок обновления и сохранения текста быть не должно.
JVM-тесты не имитируют Android UI.

`ProgressEstimatorTest.java` проверяет сглаживание скорости и прогноза за
15 секунд, ограничение частоты обновления, повторные события, паузы, смену
скорости, сброс счётчика и архивы больше 4 ГБ. Входит в `test-diagnostics.ps1`.

`ArchiveStatisticsTest.java` проверяет счётчики чтения, повторное чтение через
канал, запись, EOF, сохранение исходных ошибок и формирование статистики.
`ZipFailureTest.java` также проверяет байты статистики при настоящей распаковке
ZIP и 7z. Интерфейс статистики и сохранение после перезапуска проверяются на Android.

`test-diagnostics.ps1` компилирует платформонезависимый `DiagnosticReport`,
проверяет коды ошибок, вложенные и циклические причины, ошибки закрытия ресурсов,
сокрытие URI и ограничение размера отчёта. Дополнительные проверки исходного
кода защищают подключение отчёта к интерфейсу, отдельное сохранение и сохранность
этапа сбоя при закрытии архивов.

`SiteTransactionManagerTest.java` проверяет отдельную подготовку полной версии,
атомарное переключение каталога, восстановление прерванной первой и повторной
установки, применение всех файлов update-архива, точный расчёт места под rollback
и восстановление частично применённого обновления.

Дополнительно проверяются отмена до первого записанного блока резервной копии,
отмена посреди большого файла и восстановление после завершения процесса с
недописанной копией. Незавершённая копия находится вне каталога готовых
rollback-файлов и не может заменить действующий файл при восстановлении.

`ZipFailureTest.java` берёт методы ZIP/7z-распаковки непосредственно из текущего
`MainActivity.java` и компилирует изолированный JVM-стенд с заменой Android/UI
на заглушки. Проверяются корректные архивы, CRC, обрыв данных, отсутствие потока,
конфликт назначения, неверный заголовок 7z и одновременные ошибки чтения/закрытия.
Это не тест Android-провайдера файлов или интерфейса и не заменяет устройство.

`DemoImportFileTest.java` проверяет сохранность рабочей копии демо при удалении
соседнего каталога кэша, очистку после успеха, ошибки и прерывания процесса,
защиту активного импорта от очистки при пересоздании Activity и второго импорта.
Очистка затрагивает только известный временный файл; установленный сайт и
посторонние файлы сохраняются. Это JVM-модель очистки, а не запуск системной
очистки Android. Проверки подключения требуют `getNoBackupFilesDir()` и
освобождения рабочего файла в `finally`, в том числе при ошибке копирования.
Проверки меню также сохраняют доступ к встроенному демо после установки
пользовательского сайта и требуют подтверждения замены с возможностью отмены.

Выходные файлы находятся только в `android-webview-loader/app/build/diagnostics-tests`.
Пользовательские архивы и Builder не используются.

`test-diagnostics.ps1` сохраняется в UTF-8 с BOM и CRLF: русские строки проверок
должны одинаково читаться Windows PowerShell 5.1 и PowerShell 7.

## Ручная проверка на отдельной тестовой установке

Не очищайте данные рабочего приложения и не удаляйте рабочий сайт ради теста.
Создайте небольшие отдельные тестовые ZIP/7z, не меняя `local/site.7z` и
`local/site-update.zip`.

1. На чистой установке выберите корректный архив с `index.html`: установка
   должна завершиться без предварительного запуска демо. Повторите после демо.
2. Выберите повреждённый ZIP и повреждённый 7z: должны появиться фактический
   этап, класс и сообщение ошибки, версия APK, модель устройства и объём
   свободного места до очистки. Ошибку чтения ZIP нельзя обозначать как ошибку
   закрытия ZIP-потока.
3. Выберите корректный архив с несколькими файлами `.html` без `index.html`
   либо с обычным корневым файлом и `index.html` в каталоге: ожидается
   `GS-INDEX-CHECK`, этап поиска стартовой страницы и ненулевые счётчики
   распакованных файлов.
4. При доступности тестового провайдера проверьте отказ чтения (`GS-ACCESS`)
   и 7z из непозиционируемого потока (`GS-7Z-SEEK`). Не заполняйте рабочее
   устройство ради проверки нехватки места.
5. Нажмите «Копировать», вставьте текст в черновик сообщения. Окно должно
   остаться открытым. «Отправить» должно открыть системный выбор приложения,
   без автоматической отправки сообщения или вложения самого архива.
6. Закройте окно и перезапустите APK. Откройте `Меню → Последняя ошибка`:
   номер, время и текст отчёта должны совпадать. Успешная повторная установка
   не должна стирать отчёт.
7. Проверьте небольшой экран и крупный системный шрифт: все кнопки доступны,
   длинный отчёт прокручивается. На Android 6 проверьте копирование; на Android
   13+ не должно быть второго Toast поверх системного уведомления о копировании.
8. Если сохранение отчёта недоступно, в окне должно быть предупреждение;
   до закрытия процесса последний отчёт всё равно доступен в меню.
9. Проверьте системный возврат на Android 6–12 и жестовый возврат на Android
   13–16: из открытой игры он должен перейти по истории игры либо вернуть
   витрину, во время загрузки — отменить показ игры, а с корневой витрины —
   свернуть приложение. На Android 16 проверяйте сборку с `targetSdk 36`.

## Расширенная диагностика

`DiagnosticJournalTest.java` проверяет 20 последних действий, контрольные точки
не чаще раза в 5 секунд, незавершённую операцию после нового процесса, отказ
хранилища и отсутствие ложного сбоя после штатного завершения. Это модель
перезапуска журнала, а не имитация реального отключения питания Android.

Дополнительно на тестовом устройстве проверьте:

1. «Создать отчёт о проблеме» в меню, в том числе во время распаковки. Код —
   `GS-MANUAL`; последняя ошибка не заменяется, её фрагмент включается в отчёт.
2. Игру с намеренной ошибкой JavaScript и необработанным Promise, отсутствующим
   ресурсом и страницей. Отчёт должен содержать путь, код WebView/HTTP либо
   строку скрипта; повторяющиеся ошибки не должны создавать поток диалогов.
3. Прерывание импорта закрытием отдельного тестового процесса. После запуска
   ожидается `GS-INTERRUPTED-OPERATION` с последней сохранённой контрольной точкой,
   но без утверждения, что Android закрыл приложение именно из-за нехватки памяти.
4. Завершение процесса отображения WebView на тестовом эмуляторе/API 26+:
   `GS-WEBVIEW-RENDERER`, возврат к интерфейсу с доступным меню. Сбойная игра
   не должна автоматически открываться снова, файлы сайта остаются на месте.

Обработчики Android компилируются при сборке, но JVM-тесты не подтверждают их
работу на реальном WebView. Перехват Promise включается после загрузки документа;
ранние ошибки могут не попасть в отчёт. Системный ANR, падение всего процесса и
полное удаление данных приложения нельзя гарантированно диагностировать из него.

Прямой SDK-build передаёт классы в d8 одним промежуточным JAR, чтобы множество
вложенных Java-классов не превышало предел командной строки Windows.
