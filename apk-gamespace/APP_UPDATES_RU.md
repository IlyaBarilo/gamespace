# Обновление GameSpace APK из приложения

## Этапы внедрения

После каждого этапа выполняется проверка и делается остановка для просмотра
изменений и отдельного коммита пользователем. Git-команды агент не выполняет.

| Этап | Результат | Состояние |
| --- | --- | --- |
| 1. Каталог APK | Формат, генератор из проверенного APK, автоматические тесты | Реализован |
| 2. Публикация | Actions добавляет каталог в Pages после проверки файлов релиза | Реализован и проверен локально; требуется запуск в GitHub после коммита |
| 2.1. Объём и скорость публикации | От 3 до 10 PWA-выпусков по размеру Pages, кэш проверенных APK | Реализован; отдельный коммит перед этапом 3 |
| 3. Проверка в APK | Пункт в `⚙`, версия, описание, ручная проверка и изоляция WebView | Запланирован |
| 4. Загрузка и установка | Прогресс, отмена, проверка файла и системный установщик | Запланирован |
| 5. Проверка сценария | Сохранность данных, обработка ошибок, испытания и документация | Запланирован |

В приложении пока нет нового пункта меню или сетевых разрешений. Проверки
каталога подключены к CI, а публикация — к release workflow. Локальный
`prepare-update-catalog.mjs` не выполняет сетевых запросов; инструмент
`restore-update-catalog.mjs` читает метаданные и скачивает готовые APK из GitHub.
Оба инструмента сохраняют исходные APK и не меняют архивы сайта или PWA-пакеты.

## Сценарий после завершения всех этапов

В меню `⚙ → Обновление приложения` показываются установленная версия и дата
последней проверки. Проверка запускается отдельной кнопкой; при обычном запуске
GameSpace запросов к серверу обновлений нет. Без сети сохраняется последний
результат с его датой.

У новой версии сначала идут номер, дата, размер и описание, затем кнопка
скачивания. После загрузки и проверки появляется кнопка установки. Подтверждение
выполняется системным установщиком Android. Успех определяется при следующем
запуске по фактически установленной версии. Во время импорта, обновления,
восстановления или удаления сайта установка приложения недоступна.

Первый APK с этим механизмом устанавливается прежним способом. Обновление
поверх существующего приложения должно сохранять сайт и сохранения; требуется
совпадение идентификатора пакета и совместимая подпись. Автоматического удаления
приложения, понижения версии и бесшумной установки не предусмотрено.

PWA уже поддерживает ручную проверку и выбор версии. В APK сохраняется такой же
порядок: сведения, описание, затем действие. Системный установщик и разрешение
на установку из этого источника относятся к Android. Каталог APK отдельный;
публичная версия остаётся общей для APK и PWA.

На этапе 3 потребуется разрешение `INTERNET` для нативного кода. До его добавления
необходимо явно ограничить сетевые загрузки в обоих WebView, проверить внешние
переходы и Service Worker и исключить доступ импортированного сайта к механизму
обновления. После этого сетевую изоляцию игр обеспечивает код приложения,
а не отсутствие сетевого разрешения у всего пакета. Документация об отсутствии
`INTERNET` обновляется вместе с разрешением, не раньше.

## Формат каталога, версия схемы 1

Адрес после успешного запуска обновлённого release workflow:
`https://ilyabarilo.github.io/gamespace/apk/updates.json`.
Сам коммит не публикует каталог. JSON имеет UTF-8, без BOM, с CRLF.

| Поле | Значение |
| --- | --- |
| `schemaVersion` | `1`; неизвестная схема должна быть отклонена клиентом |
| `applicationId` | `ru.local.gamespace.loader` |
| `channel` | `stable` |
| `latestVersionCode` | Наибольший `versionCode` среди записей |
| `releases` | До 100 записей, от новых к старым, без повторов |

Каждая запись содержит:

| Поле | Источник и назначение |
| --- | --- |
| `tag`, `version` | Канонический тег релиза и нормализованная версия `MAJOR.MINOR.PATCH` |
| `versionCode` | Значение APK; должно совпадать с `MAJOR * 10000 + MINOR * 100 + PATCH` |
| `publishedAt` | `published_at` релиза, UTC в формате `YYYY-MM-DDTHH:MM:SSZ` |
| `description` | Текст GitHub Release; пустое описание допустимо |
| `releaseUrl` | Страница этого релиза в официальном репозитории |
| `minSdk` | Минимальная версия API Android из проверенного APK |
| `apk.name`, `apk.url` | `GameSpace-<version>.apk` и HTTPS-ссылка на файл конкретного тега |
| `apk.size`, `apk.sha256` | Размер в байтах и SHA-256 фактического файла |
| `apk.signerSha256` | SHA-256 сертификата подписанта APK |

`GameSpace-latest.apk` не используется для скачивания из приложения: ссылка
должна однозначно указывать на проверенную версию. Каталог не объявляет
релиз готовым только по наличию тега или страницы GitHub Release.

Ограничения: JSON не более 1 МиБ, описание одного релиза не более 32 КиБ UTF-8,
размер APK и `versionCode` — положительные целые до `2147483647`. `MINOR`
и `PATCH` лежат в диапазоне 0–99, как в существующей сборке APK. Описание
хранится как текст, без исполнения HTML, скриптов или команд. Переносы строк
в описании нормализуются в LF внутри JSON-строки.

Этап 1 проверяет один сертификат подписанта и его совпадение с явно переданным
ожидаемым отпечатком. Ротация ключей и несколько подписантов требуют отдельного
решения. Отпечаток из скачанного каталога не является доверенным ключом:
будущий клиент должен сверять APK с подписью уже установленного приложения,
а окончательное решение об установке принимает Android.

## Генерация и проверки

Инструменты находятся в `apk-gamespace/scripts/` и используют только встроенные
модули Node.js 20+. Дополнительно нужны Java и Android SDK Build Tools:
`aapt2` и `lib/apksigner.jar`. Новых npm-зависимостей нет.

Входные файлы:

- APK, скачанный из уже опубликованного стабильного релиза после проверки
  загруженных файлов; исходный файл открывается только на чтение.
- JSON ответа GitHub REST `GET /repos/IlyaBarilo/gamespace/releases/tags/<tag>`.
  Используются `tag_name`, `draft`, `prerelease`, `published_at`, `body`,
  `html_url`, `assets[].name/size/state/browser_download_url/digest`.
- Предыдущий каталог через `--previous` при наличии опубликованного каталога.
- Ожидаемый SHA-256 сертификата через `--expected-signer-sha256` из доверенного
  процесса подписания. Нельзя брать его из того же непроверенного каталога.

Справка по параметрам, из корня проекта:

```cmd
node apk-gamespace/scripts/prepare-update-catalog.mjs --help
```

Вызов для подготовленных локальных входных файлов; значения в угловых скобках
нужно заменить реальными путями и отпечатком:

```cmd
node apk-gamespace/scripts/prepare-update-catalog.mjs --apk "<file.apk>" --release "<release.json>" --aapt2 "<SDK>/aapt2.exe" --apksigner-jar "<SDK>/lib/apksigner.jar" --java "<JDK>/bin/java.exe" --expected-signer-sha256 "<64 hex digits>" --previous "<previous/updates.json>" --output "<new-pages/apk/updates.json>"
```

При ручном объединении параметр `--previous` отсутствует только у первого
элемента. Указанный, но недоступный или повреждённый каталог вызывает ошибку.
Повтор старого релиза с прежним каталогом сохраняет последней более новую версию.
Повтор той же версии допускает уточнение описания, но запрещает замену APK,
его подписи, размера, минимального API и даты публикации. Автоматический workflow
восстанавливает цепочку из файлов GitHub Releases, как описано ниже.

Генератор проверяет код завершения `apksigner verify --verbose --print-certs`,
читает идентификатор, версии и `minSdk` через `aapt2 dump badging`, вычисляет
SHA-256 потоком и сверяет размер с GitHub. При наличии `assets[].digest`
проверяется и эта сумма. Для старых файлов GitHub без `digest` обязательна
проверка скачанных байтов в процессе публикации; локальная генерация сама
по себе не доказывает, что файл действительно скачан по указанному URL.

Результат записывается в новый `updates.json` внутри каталога подготовки Pages.
Существующий выходной файл не перезаписывается. Любой сбой должен останавливать
публикацию; каталог подготовки после сбоя не считается готовым к развёртыванию.

Описание SDK-команд: [apksigner](https://developer.android.com/tools/apksigner)
и [AAPT2](https://developer.android.com/tools/aapt2).

## Автоматическая публикация

CI по push и pull request сохраняет отдельные задания PWA на Linux и APK
на Windows. После сборки APK с тестовой подписью запускаются тесты генерации
и восстановления каталога, включая проверку настоящими SDK-инструментами.
Релизные секреты в CI не используются.

Release workflow по-прежнему запускается при публикации стабильного релиза
или вручную с его тегом. Последовательность:

1. `validate` проверяет релиз; `pwa` и `apk` независимо собирают и проверяют
   приложения из тега. PWA-пакеты передаются дальше отдельным артефактом
   `pwa-release-packages`, включая скрытые файлы. Задание APK получает отпечаток
   сертификата из новой сборки с доверенным релизным ключом до повторного
   использования прежних APK. Новых секретов не требуется.
2. `publish` добавляет только недостающие файлы, затем скачивает все три
   файла текущего релиза и сравнивает их с подготовленными байтами.
3. `pages` получает проверенные пакеты и запускает тесты каталога на Linux
   с настоящим SDK. Инструменты этого задания берутся из коммита запускаемого
   workflow (`github.workflow_sha`), поэтому ручной повтор старого релиза
   не требует наличия новых скриптов внутри его неизменяемого тега.
4. `restore-update-catalog.mjs` получает последние 100 стабильных релизов
   GitHub и дополнительно текущий тег, если тот отсутствует в списке. Для
   включения записи нужны загруженные версионный APK, `GameSpace-latest.apk`
   и PWA-пакет. Незавершённые прошлые релизы пропускаются с сообщением;
   незавершённый текущий релиз вызывает ошибку.
5. Для новых APK и записей без подходящего кэша обе копии скачиваются и
   сравниваются; версионный APK проверяется через SDK с ожидаемым сертификатом
   текущей доверенной сборки. Ошибка API,
   скачивания, подписи или контрольной суммы останавливает публикацию.
   Неверная подпись готового прошлого релиза также вызывает ошибку, а не
   скрытое исключение его из каталога.
6. Уже опубликованный `apk/updates.json` используется только как кэш проверок.
   Повторное использование требует совпадения SHA-256 и размера обеих копий
   по текущим данным GitHub, даты публикации и ожидаемого сертификата.
   Описание берётся заново из Release. Если GitHub не вернул `digest` хотя бы
   одного APK, выполняется полная проверка. Недоступный или повреждённый кэш
   также приводит к полной проверке, а не к потере истории. Список выпусков
   всегда берётся из GitHub Releases; удалённые и незавершённые выпуски
   не сохраняются в каталоге только из-за присутствия в кэше.
7. Для корня Pages выбирается наибольшая проверенная версия APK. Её проверенный
   PWA-пакет должен присутствовать в переданном наборе. Финальная сборка
   повторно проверяет PWA-манифесты и runtime, добавляет каталог в `apk/updates.json`
   вне `releases/<версия>/`. Обязательны три последние PWA-версии; более старые
   добавляются по порядку до десяти, пока весь сайт укладывается в 900 000 000
   байт. При первом превышении оставшаяся история не берётся. Размер JSON APK,
   корневой копии и метаданных учитывается заранее. Если не помещаются даже три
   обязательные версии, `deploy` не запускается. Это запас ниже ограничения
   GitHub Pages в 1 ГБ. Если выпусков пока меньше трёх, включаются все доступные.

Кэш запрашивается только по официальному HTTPS-адресу, без GitHub-токена,
без перенаправлений, с тайм-аутом 15 секунд и пределом 1 МиБ. Его отпечаток
сертификата сверяется с доверенной сборкой; сам кэш не задаёт доверенный ключ.
В workflow кэш включён параметром `--use-published-cache`. Без этого параметра
`restore-update-catalog.mjs` заново скачивает и проверяет APK всех выбранных
готовых релизов. Первый запуск может быть дольше последующих.

Ограничение APK-каталога в 100 записей относится к сведениям для обновления,
а ограничение PWA в 10 выпусков — к файлам на Pages. Скрипты не удаляют
GitHub Releases или их assets. Подробности хранения и обновления установленной
старой PWA: [RELEASING_RU.md](../pwa-gamespace/RELEASING_RU.md).

Повтор старого релиза сохраняет более новую готовую версию последней. При
сбое подготовки каталога или Pages `deploy` не запускается: прежний сайт
остаётся доступным. APK и PWA, уже добавленные в GitHub Release до этого сбоя,
сохраняются; повторный запуск проверяет их и продолжает подготовку.

Обработчик тегов PWA исправлен и защищён тестами: `v1.0.1` и `v0.0.1`
сохраняют нулевой `MINOR` при ненулевом `PATCH`.

## Следующий этап

Этап 3 добавит экран ручной проверки в APK, сведения о текущей и доступной
версиях, сохранение последнего результата и обработку отсутствия сети.
Добавление `INTERNET` выполняется вместе с явной изоляцией WebView и проверкой
того, что импортированные игры не получают сетевой доступ или управление
обновлением приложения. Скачивание и установщик относятся к этапу 4.

Проверки выполненных этапов и способы их запуска описаны в
[tests/README.md](tests/README.md). Проверки генератора не подтверждают работу
будущего интерфейса или установщика на устройстве.
